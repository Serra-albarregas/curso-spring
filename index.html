03 · Lombok

Lombok — Eliminar el boilerplate

Lombok es una librería que genera automáticamente código Java repetitivo (getters, setters, constructores, toString…) mediante anotaciones procesadas en tiempo de compilación. El código generado es idéntico al que escribirías a mano, pero tú no lo ves ni lo mantienes.

Instalación

pom.xmlXML
<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <optional>true</optional>  <!-- no se empaqueta en el JAR final -->
</dependency>
🖥️
En VS Code, instala la extensión Lombok Annotations Support for VS Code (ID: vscjava.vscode-lombok) para que el editor reconozca los métodos generados y no muestre errores falsos.

@Getter y @Setter

Generan automáticamente los métodos getX() y setX() para cada campo. Pueden aplicarse a nivel de clase (todos los campos) o en un campo concreto.

Sin Lombok
public class Libro {
    private String titulo;
    private BigDecimal precio;
    private Integer stock;

    public String getTitulo() {
        return titulo;
    }
    public void setTitulo(String titulo) {
        this.titulo = titulo;
    }
    public BigDecimal getPrecio() {
        return precio;
    }
    public void setPrecio(BigDecimal precio) {
        this.precio = precio;
    }
    public Integer getStock() {
        return stock;
    }
    public void setStock(Integer stock) {
        this.stock = stock;
    }
}
→
Con Lombok
@Getter
@Setter
public class Libro {
    private String titulo;
    private BigDecimal precio;
    private Integer stock;
}

// Lombok genera exactamente los mismos
// 6 métodos que ves a la izquierda.
// El bytecode compilado es idéntico.
@Getter                           // getters en todos los campos
public class Libro {
    private String titulo;

    @Setter                         // setter solo en este campo
    private Integer stock;

    // precio: solo getter (de la anotación de clase), sin setter
    private BigDecimal precio;
}

Constructores automáticos

@NoArgsConstructor
Genera un constructor sin argumentos. Obligatorio para entidades JPA, que exigen un constructor por defecto.
@Entity
@NoArgsConstructor        // JPA lo requiere
public class Libro { ... }
@AllArgsConstructor
Genera un constructor con todos los campos de la clase como argumentos, en el orden en que están declarados.
@AllArgsConstructor
public class ErrorResponse {
    private String codigo;
    private String mensaje;
}
// new ErrorResponse("NOT_FOUND", "...");
@RequiredArgsConstructor
Genera un constructor solo con los campos final o anotados con @NonNull. Es la pareja perfecta de la inyección por constructor en Spring.
@Service
@RequiredArgsConstructor  // genera constructor con repo + email
public class PedidoService {
    private final ProductoRepository repo;
    private final EmailService email;
    // sin código adicional
}

@Data — La combinación completa

@Data es una meta-anotación que equivale a poner @Getter + @Setter + @RequiredArgsConstructor + @ToString + @EqualsAndHashCode al mismo tiempo.

Ejemplo con @DataJava
@Data                            // getters + setters + constructor + toString + equals/hashCode
public class LibroDTO {
    private String titulo;
    private BigDecimal precio;
    private String genero;
}

// Equivale exactamente a escribir todo esto a mano:
// getTitulo(), setTitulo(), getPrecio(), setPrecio(), getGenero(), setGenero(),
// LibroDTO(String titulo, BigDecimal precio, String genero),
// toString(), equals(), hashCode()
⚠️
No uses @Data en entidades JPA. El equals() y hashCode() que genera usa todos los campos, lo que causa problemas con las colecciones lazy de Hibernate. En entidades usa @Getter + @Setter + @NoArgsConstructor + @EqualsAndHashCode(onlyExplicitlyIncluded = true).

@Builder — Patrón Builder automático

Genera una clase interna estática Builder que permite construir objetos con una sintaxis fluida y legible. Especialmente útil en tests para crear objetos complejos con solo los campos relevantes.

@Builder en acciónJava
@Builder
@Getter
public class Libro {
    private String     titulo;
    private String     isbn;
    private BigDecimal precio;
    private Integer    stock;
    private String     genero;
}

// Crear un libro con solo los campos que interesan — ideal en tests
Libro libro = Libro.builder()
    .titulo("Clean Code")
    .precio(new BigDecimal("35.90"))
    .stock(100)
    .build();

// Con toBuilder=true puedes clonar y modificar
@Builder(toBuilder = true)
public class Libro { ... }

Libro rebajado = libro.toBuilder()
    .precio(new BigDecimal("19.99"))  // solo cambia el precio
    .build();

@Slf4j — Logging sin boilerplate

Genera automáticamente el campo de logger estándar SLF4J. Sin Lombok necesitas escribir siempre la misma línea en cada clase.

Sin Lombok
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@Service
public class PedidoService {

    // Esta línea en CADA clase

        LoggerFactory.getLogger(
            PedidoService.class);

    public void procesar() {
        log.info("Procesando...");
    }
}
→
Con Lombok
@Slf4j
@Service
public class PedidoService {

    // log disponible directamente



    public void procesar() {
        log.info("Procesando...");
        log.debug("Detalle: {}", dato);
        log.error("Error", ex);
    }
}

@ToString y @EqualsAndHashCode

Uso correcto en entidades JPAJava
@Entity
@Getter @Setter
@NoArgsConstructor
@ToString(exclude = "libros")             // ① excluye colecciones para evitar bucle infinito
@EqualsAndHashCode(onlyExplicitlyIncluded = true)  // ② solo usa el @Id
public class Autor {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    @EqualsAndHashCode.Include            // ③ solo este campo determina igualdad
    private Long id;

    private String nombre;

    @OneToMany(mappedBy = "autor", fetch = FetchType.LAZY)
    @ToString.Exclude                     // ④ también se puede excluir campo a campo
    private List<Libro> libros;
}
ℹ️
En entidades JPA, nunca incluyas colecciones @OneToMany en toString(). Dispararía una query SQL (lazy loading) cada vez que se loguea el objeto, y podría causar un bucle infinito si hay relaciones bidireccionales.

@NonNull — Validación en tiempo de ejecución

Genera una comprobación de nulidad al inicio del método o constructor. Si el argumento es null, lanza NullPointerException con un mensaje claro.

@Service
@RequiredArgsConstructor
public class PedidoService {

    // @NonNull en el parámetro del constructor genera:
    // if (repo == null) throw new NullPointerException("repo is marked non-null but is null");
    private final @NonNull ProductoRepository repo;

    public Pedido crear(@NonNull PedidoDTO dto) {  // también en parámetros de métodos
        // si dto == null, falla aquí con mensaje claro, no en algún sitio inesperado
        return repo.save(mapper.toEntity(dto));
    }
}

Receta para entidades JPA

La combinación correcta para una entidad JPA evita todos los problemas comunes de Lombok con Hibernate:

Patrón recomendado para @EntityJava
@Entity
@Table(name = "libros")
@Getter                                              // ✅ getters en todos
@Setter                                              // ✅ setters en todos
@NoArgsConstructor                                   // ✅ exigido por JPA
@ToString(exclude = "autor")                         // ✅ excluye relaciones
@EqualsAndHashCode(onlyExplicitlyIncluded = true)    // ✅ solo el @Id
public class Libro {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    @EqualsAndHashCode.Include                        // ✅ igualdad basada en ID
    private Long id;

    private String titulo;
    private BigDecimal precio;

    @ManyToOne(fetch = FetchType.LAZY)
    private Autor autor;
}

04 · IoC & DI

IoC e Inyección de Dependencias

El problema que resuelve

Imagina que tienes un servicio de pedidos que necesita acceder a la base de datos y enviar emails. Sin Spring, tú mismo crearías y gestionarías esos objetos:

public class PedidoService {

    // ❌ PedidoService crea sus propias dependencias
    // Problemas: acoplamiento fuerte, imposible de testear en aislamiento,
    // cada cambio de implementación obliga a modificar esta clase
    private ProductoRepository repo  = new ProductoRepositoryImpl();
    private EmailService       email = new SmtpEmailService("smtp.gmail.com", 587);

    public void procesarPedido(Pedido p) {
        repo.guardar(p);
        email.enviar(p.getCliente(), "Pedido confirmado");
    }
}

Esto tiene tres grandes problemas: acoplamiento (la clase decide qué implementación concreta usar), rigidez (si quieres cambiar a SendGrid en lugar de SMTP, tienes que modificar el código), y imposibilidad de testear en aislamiento sin conectarse de verdad a la base de datos y al servidor de correo.

Inversion of Control (IoC)

IoC es el principio de diseño que dice: «no crees tus dependencias, deja que alguien externo te las proporcione». En Spring, ese «alguien externo» es el contenedor IoC (también llamado ApplicationContext).

El control de la creación de objetos se invierte: antes era la clase la que creaba sus dependencias; ahora es el contenedor el que las crea y las inyecta.

Dependency Injection (DI)

La Inyección de Dependencias es el mecanismo concreto con el que Spring implementa IoC. Spring instancia los objetos que necesitas y los «inyecta» en tu clase automáticamente. Tú solo declaras qué necesitas.

@Service
public class PedidoService {

    // ✅ PedidoService DECLARA lo que necesita, no lo crea
    // Spring se encarga de construir y proporcionar las implementaciones
    private final ProductoRepository repo;
    private final EmailService       email;

    public PedidoService(ProductoRepository repo, EmailService email) {
        this.repo  = repo;
        this.email = email;
    }

    public void procesarPedido(Pedido p) {
        repo.guardar(p);
        email.enviar(p.getCliente(), "Pedido confirmado");
    }
}

Ahora, si mañana cambias de SMTP a SendGrid, PedidoService no cambia en absoluto. Solo registras la nueva implementación y Spring la inyecta. Además, en los tests puedes inyectar un mock que no envíe correos de verdad.

Los 3 tipos de inyección

1. Inyección por Constructor ✅ Recomendada

Las dependencias se proporcionan como argumentos del constructor. Es la forma preferida porque hace las dependencias obligatorias y visibles, los campos pueden ser final (inmutables), y facilita el testing sin Spring.

@Service
public class PedidoService {

    // final garantiza que no cambian después de la construcción
    private final ProductoRepository repo;
    private final EmailService       email;
    private final StockService        stock;

    // Con un solo constructor, @Autowired es opcional desde Spring 4.3
    public PedidoService(ProductoRepository repo,
                          EmailService email,
                          StockService stock) {
        this.repo  = repo;
        this.email = email;
        this.stock = stock;
    }
}

// Con Lombok @RequiredArgsConstructor — genera el constructor automáticamente:
@Service
@RequiredArgsConstructor   // genera constructor con todos los campos final
public class PedidoService {
    private final ProductoRepository repo;
    private final EmailService       email;
    private final StockService        stock;
    // sin código adicional: Lombok escribe el constructor
}
✅ Ventajas
  • Dependencias obligatorias: si falta una, falla al arrancar
  • Campos final: inmutabilidad garantizada
  • Se puede testear sin Spring: new PedidoService(mockRepo, mockEmail, mockStock)
  • Las dependencias son explícitas en la firma del constructor

2. Inyección por Setter ⚠️ Para dependencias opcionales

Spring llama al método setter después de construir el objeto. Útil solo cuando la dependencia es opcional o puede cambiar durante el ciclo de vida del bean.

@Service
public class ReporteService {

    private NotificadorService notificador; // sin final: puede ser null

    // Spring llama a este setter después de crear el bean
    @Autowired(required = false)  // required=false: no falla si no hay implementación
    public void setNotificador(NotificadorService notificador) {
        this.notificador = notificador;
    }

    public void generarReporte() {
        // hay que comprobar null porque es opcional
        if (notificador != null) {
            notificador.avisar("Reporte generado");
        }
    }
}

3. Inyección por Campo ❌ Evitar en producción

Spring inyecta directamente en el campo usando reflexión. Es la forma más corta de escribir pero tiene serios inconvenientes.

@Service
public class PedidoService {

    @Autowired
    private ProductoRepository repo;   // ❌ oculta la dependencia

    @Autowired
    private EmailService email;         // ❌ no puede ser final
}
❌ Problemas de la inyección por campo
  • Testing sin Spring imposible: no hay forma de inyectar mocks sin usar reflexión
  • Dependencias ocultas: no se ven en la firma del constructor ni en los setters
  • No puede ser final: la reflexión exige que el campo sea modificable
  • Dependencias circulares enmascaradas: Spring puede no detectarlas hasta el arranque

Múltiples implementaciones: @Qualifier y @Primary

¿Qué ocurre si tienes varias implementaciones de la misma interfaz y Spring no sabe cuál inyectar?

// Dos implementaciones de la misma interfaz
@Service("smtpEmail")
public class SmtpEmailService implements EmailService { ... }

@Service("sendgridEmail")
public class SendGridEmailService implements EmailService { ... }

// Opción A — @Qualifier: elige por nombre
@Service
@RequiredArgsConstructor
public class PedidoService {
    @Qualifier("sendgridEmail")
    private final EmailService email;   // inyecta SendGridEmailService
}

Dependencias circulares

Una dependencia circular ocurre cuando A necesita B y B necesita A. Spring lo detecta al arrancar con inyección por constructor y lanza un error claro. Es una señal de que el diseño necesita revisión.

// ❌ Dependencia circular — Spring lanza BeanCurrentlyInCreationException
@Service
public class ServicioA {
    private final ServicioB b;
    public ServicioA(ServicioB b) { this.b = b; }
}

@Service
public class ServicioB {
    private final ServicioA a;
    public ServicioB(ServicioA a) { this.a = a; }
}

// ✅ Solución: extraer la lógica común a un tercer servicio
@Service
public class ServicioComun { ... }  // A y B dependen de esto, no entre sí

¿Cómo funciona el contenedor por dentro?

Al arrancar, Spring escanea el classpath buscando clases anotadas con @Component y sus derivadas. Construye un grafo de dependencias y los instancia en el orden correcto:

// Spring detecta estas clases automáticamente por @ComponentScan

@Repository  // ① Spring instancia esto primero (no tiene dependencias)
public class ProductoRepositoryImpl implements ProductoRepository { ... }

@Service     // ② Spring instancia esto segundo (depende de ProductoRepository)
public class StockService {
    private final ProductoRepository repo;
    public StockService(ProductoRepository repo) { this.repo = repo; }
}

@Service     // ③ Spring instancia esto último (depende de StockService)
public class PedidoService {
    private final StockService stock;
    public PedidoService(StockService stock) { this.stock = stock; }
}

// Spring calcula el orden: ProductoRepository → StockService → PedidoService
// Tú no tienes que preocuparte por el orden de creación
💡

Configuración completa con JWT (Spring Boot 3)

@Configuration
@EnableWebSecurity
@EnableMethodSecurity                    // activa @PreAuthorize, @PostAuthorize
@RequiredArgsConstructor
public class SecurityConfig {

    private final JwtAuthFilter         jwtFilter;
    private final UserDetailsService    userDetailsService;

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            // Sin CSRF en APIs stateless (JWT ya lo protege)
            .csrf(csrf -> csrf.disable())

            // Sin sesión HTTP: cada petición lleva el token
            .sessionManagement(s -> s
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS))

            // Reglas de acceso por ruta
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()         // login y registro
                .requestMatchers("/actuator/health").permitAll()     // health check
                .requestMatchers("/swagger-ui/**").permitAll()       // documentación
                .requestMatchers(HttpMethod.GET, "/api/libros/**")
                    .hasAnyRole("USER", "ADMIN")                    // GET solo con USER o ADMIN
                .requestMatchers("/api/admin/**").hasRole("ADMIN")  // admin completo
                .anyRequest().authenticated()
            )

            // Nuestro filtro JWT va antes del filtro de usuario/contraseña
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
            .build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(12);   // factor 12: ~300ms/hash, seguro
    }

    @Bean
    public AuthenticationManager authManager(AuthenticationConfiguration cfg)
            throws Exception {
        return cfg.getAuthenticationManager();
    }
}

Filtro JWT personalizado

@Component
@RequiredArgsConstructor
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtService         jwtService;
    private final UserDetailsService  userDetailsService;

    @Override
    protected void doFilterInternal(
            HttpServletRequest  req,
            HttpServletResponse res,
            FilterChain         chain) throws ServletException, IOException {

        // 1. Extraer el token del header Authorization: Bearer <token>
        String header = req.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(req, res);   // sin token: continuar (el auth lo bloqueará si es necesario)
            return;
        }

        String token    = header.substring(7);
        String username = jwtService.extractUsername(token);

        // 2. Si hay usuario y no está autenticado aún en este hilo
        if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {
            UserDetails user = userDetailsService.loadUserByUsername(username);

            // 3. Validar el token (firma, expiración…)
            if (jwtService.isValid(token, user)) {
                var auth = new UsernamePasswordAuthenticationToken(
                    user, null, user.getAuthorities());
                auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));

                // 4. Registrar en el SecurityContext del hilo actual
                SecurityContextHolder.getContext().setAuthentication(auth);
            }
        }
        chain.doFilter(req, res);
    }
}

08 · Avanzado

Programación Orientada a Aspectos (AOP)

AOP permite añadir comportamiento transversal (logging, métricas, auditoría, seguridad) a múltiples clases sin modificar su código. Spring implementa AOP mediante proxies dinámicos: cuando llamas a un bean Spring, en realidad llamas a un proxy que puede ejecutar código antes, después o alrededor del método real.

¿Por qué AOP?

Sin AOP, el logging de tiempo de ejecución requiere copiar el mismo código en cada método de cada servicio. Con AOP, se escribe una vez y se aplica a todos automáticamente:

public LibroDTO crear(LibroRequestDTO dto) {
    long inicio = System.currentTimeMillis();  // ← duplicado
    try {
        LibroDTO result = /* lógica real */;
        log.info("crear → {} ms", System.currentTimeMillis() - inicio); // ← duplicado
        return result;
    } catch (Exception e) {
        log.error("Error en crear", e);  // ← duplicado
        throw e;
    }
}
// Y lo mismo en obtener(), actualizar(), eliminar()... decenas de veces
@Around("execution(* com.ejemplo.service.*.*(..))")
public Object logTiempo(ProceedingJoinPoint jp) throws Throwable {
    long t = System.currentTimeMillis();
    try {
        Object r = jp.proceed();
        log.info("{} → {} ms", jp.getSignature(), System.currentTimeMillis() - t);
        return r;
    } catch (Exception e) { log.error("Error en {}", jp.getSignature(), e); throw e; }
}
// Se aplica automáticamente a TODOS los métodos de TODOS los servicios

// 1. Definir la anotación personalizada
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Auditable {
    String accion() default "";
}

// 2. Usarla en el servicio
@Auditable(accion = "CREAR_LIBRO")
public LibroDTO crear(LibroRequestDTO dto) { ... }

// 3. El aspecto la intercepta automáticamente
@Aspect @Component @Slf4j @RequiredArgsConstructor
public class AuditoriaAspect {

    private final AuditoriaRepository auditoriaRepo;

    @AfterReturning(
        pointcut = "@annotation(auditable)",
        returning = "resultado")
    public void auditar(JoinPoint jp, Auditable auditable, Object resultado) {
        String usuario = SecurityContextHolder.getContext()
            .getAuthentication().getName();
        auditoriaRepo.save(new AuditLog(
            auditable.accion(), usuario,
            jp.getArgs(), LocalDateTime.now()));
        log.info("[AUDIT] {} ejecutó {} con resultado: {}",
            usuario, auditable.accion(), resultado);
    }
}

Spring WebFlux — Programación Reactiva

WebFlux es el módulo web reactivo de Spring, construido sobre Project Reactor. A diferencia de Spring MVC que bloquea un hilo por petición, WebFlux usa un event loop que gestiona miles de peticiones concurrentes con muy pocos hilos, sin bloquear mientras espera I/O.

El modelo reactivo vs. el bloqueante

Spring MVC (bloqueante)Spring WebFlux (reactivo)
ModeloUn hilo por petición (thread-per-request)Pocos hilos, event loop no bloqueante
I/OEl hilo espera bloqueado hasta que llega la respuestaEl hilo procesa otras peticiones mientras espera
Tipo de retornoString, Object, ResponseEntityMono<T> (0-1 elementos), Flux<T> (0-N)
BDJPA / JDBC (bloqueante)R2DBC (reactivo no bloqueante)
Curva de aprendizajeBajaAlta (paradigma diferente)
Ideal paraAPIs CRUD estándarAlta concurrencia, streaming, microservicios que agregan múltiples APIs

Controller reactivo completo

@RestController
@RequestMapping("/api/v1/libros")
@RequiredArgsConstructor
public class LibroReactiveController {

    private final LibroReactiveRepository repo;
    private final LibroMapper             mapper;

    // Flux: lista completa (no bloqueante)
    @GetMapping
    public Flux<LibroDTO> listar() {
        return repo.findAll().map(mapper::toDTO);
    }

    // Mono: un elemento o error 404
    @GetMapping("/{id}")
    public Mono<ResponseEntity<LibroDTO>> obtener(@PathVariable Long id) {
        return repo.findById(id)
            .map(mapper::toDTO)
            .map(ResponseEntity::ok)
            .defaultIfEmpty(ResponseEntity.notFound().build());
    }

    // Server-Sent Events: stream en tiempo real
    @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<LibroDTO> stream() {
        return repo.findAll()
            .map(mapper::toDTO)
            .delayElements(Duration.ofMillis(200));   // 1 libro cada 200ms
    }

    // POST reactivo
    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public Mono<LibroDTO> crear(@RequestBody @Valid Mono<LibroRequestDTO> bodyMono) {
        return bodyMono
            .map(mapper::toEntity)
            .flatMap(repo::save)               // flatMap para operaciones asíncronas
            .map(mapper::toDTO);
    }

    // Combinar dos fuentes de datos en paralelo
    @GetMapping("/enriquecido/{id}")
    public Mono<LibroEnriquecidoDTO> enriquecido(@PathVariable Long id) {
        Mono<Libro>   libro  = repo.findById(id);
        Mono<Opinion> opinion = opinionService.obtener(id);  // llamada externa

        return Mono.zip(libro, opinion, LibroEnriquecidoDTO::new);  // en paralelo
    }
}

repo.findById(id)

        e -> new ServiceException("Error de BD", e))

Circuit Breaker y Retry con Resilience4j

@Service
@RequiredArgsConstructor
public class PagoService {

    private final PagoApiClient apiClient;

    // Circuit Breaker: si falla N veces seguidas, se "abre" y llama al fallback
    // Retry: reintenta hasta 3 veces antes de abrir el circuito
    @CircuitBreaker(name = "pagos", fallbackMethod = "pagoFallback")
    @Retry(name = "pagos")
    @TimeLimiter(name = "pagos")              // timeout máximo de la llamada
    public CompletableFuture<PagoResponse> procesar(PagoRequest req) {
        return CompletableFuture.supplyAsync(() -> apiClient.pagar(req));
    }

    public CompletableFuture<PagoResponse> pagoFallback(PagoRequest req, Throwable t) {
        log.warn("Pago diferido para pedido {}: {}", req.getId(), t.getMessage());
        return CompletableFuture.completedFuture(PagoResponse.pendiente(req.getId()));
    }
}

JPA — Conceptos y arquitectura

JPA (Jakarta Persistence API) es una especificación Java estándar que define cómo mapear objetos Java a tablas de una base de datos relacional. Hibernate es la implementación más usada de JPA. Spring Data JPA añade una capa de abstracción sobre Hibernate que elimina el código boilerplate de repositorios.

📋
JPA
Especificación (interfaz). Define las anotaciones @Entity, @Id, @OneToMany… y la API EntityManager. No implementa nada.
🔧
Hibernate
Implementación de JPA. Traduce operaciones de objetos a SQL, gestiona el caché de primer nivel, el contexto de persistencia y el lazy loading.
🚀
Spring Data JPA
Capa de abstracción sobre Hibernate. Genera repositorios automáticamente, deriva queries del nombre del método y elimina todo el boilerplate de EntityManager.

La pila completa

Cuando llamas a libroRepo.findById(1L) en tu servicio, la petición desciende por cuatro capas antes de llegar a la base de datos. Entender esta cadena es clave para saber dónde buscar cuando algo falla o es lento: Spring Data JPA transforma la llamada al método en una query JPQL, Hibernate compila esa JPQL en SQL específico del dialecto de la BD, el driver JDBC envía el SQL a través de la red, y la base de datos lo ejecuta y devuelve filas. El resultado asciende en sentido contrario, y Hibernate materializa las filas como objetos Java antes de que Spring los devuelva a tu código.

El Contexto de Persistencia

El contexto de persistencia (o sesión Hibernate) es el núcleo de JPA. Es un caché de primer nivel que actúa como buffer entre tu código Java y la base de datos. Cada entidad cargada dentro de una transacción queda "vigilada" (managed) por Hibernate.

Estado de la entidadDescripciónHibernate la rastrea
TransientObjeto creado con new, no asociado a ninguna sesión❌ No
ManagedCargada desde la BD o guardada con save() dentro de una TX. Hibernate detecta cambios automáticamente✅ Sí
DetachedLa transacción terminó. El objeto ya no está en el contexto pero tiene ID. Los cambios NO se persisten❌ No
RemovedMarcada para borrar con delete(). Se elimina al hacer flush✅ Sí (para borrar)
@Transactional
public void ejemplo() {
    // TRANSIENT: new sin persistir
    Libro libro = new Libro();
    libro.setTitulo("Clean Code");

    // MANAGED: Hibernate rastrea este objeto
    Libro guardado = repo.save(libro);

    // Cambio AUTOMÁTICO: Hibernate detecta la modificación
    // y hará UPDATE al final de la TX sin llamar a save() de nuevo
    guardado.setPrecio(new BigDecimal("35.90"));

} // Al salir: flush → commit → objeto pasa a DETACHED

// Fuera de la TX: DETACHED
public void fueraDeTx(Libro libro) {
    libro.setTitulo("Nuevo título");  // NO se persistirá, está detached
}
💡
Dirty checking: dentro de una transacción, Hibernate compara el estado inicial de cada entidad managed con su estado al hacer flush. Si hay diferencias, genera automáticamente el UPDATE correspondiente. No necesitas llamar a save() para actualizar una entidad que ya está managed.

Configuración en application.yml

La mayoría de las propiedades de Hibernate tienen valores por defecto razonables para desarrollo, pero hay varias que es imprescindible revisar antes de ir a producción. ddl-auto controla si Hibernate debe crear, actualizar o solo validar el esquema al arrancar — en producción siempre validate, delegando la gestión del esquema a una herramienta de migraciones. open-in-view debe desactivarse porque su valor por defecto (true) mantiene la sesión de Hibernate abierta durante toda la petición HTTP, provocando queries lazy silenciosas fuera de la capa de servicio. Las propiedades de batch_size mejoran el rendimiento en inserciones masivas sin cambiar una sola línea de código Java.

jpa: hibernate: ddl-auto: validate # validate | update | create | create-drop | none show-sql: false # true solo en desarrollo open-in-view: false # IMPORTANTE: desactiva el antipatrón OSIV properties: hibernate: format_sql: true # formato legible en el log use_sql_comments: true # añade comentario con JPQL antes del SQL default_batch_fetch_size: 25 # optimiza queries N+1 con IN() jdbc: batch_size: 25 # agrupar INSERTs/UPDATEs en lote order_inserts: true order_updates: true dialect: org.hibernate.dialect.PostgreSQLDialect
⚠️
Open Session In View (OSIV) está activado por defecto en Spring Boot y es un antipatrón: mantiene la sesión Hibernate abierta durante toda la petición HTTP, lo que provoca queries lazy inesperadas en la capa de vista. Desactívalo siempre con open-in-view: false.

Configuración de la base de datos

Spring Boot necesita saber cómo conectarse a la base de datos. Toda esa configuración vive en src/main/resources/application.properties (o application.yml). No hay que escribir ni una línea de código Java: Spring Boot lee el fichero al arrancar, configura automáticamente el pool de conexiones HikariCP e inicializa Hibernate con los parámetros indicados.

application.properties explicado propiedad a propiedad

El siguiente fichero es un ejemplo completo para conectarse a una base de datos MySQL en local con las propiedades más habituales en un proyecto de desarrollo:

src/main/resources/application.propertiesProperties
# ── Nombre de la aplicación ──────────────────────────────────────────
# Identifica la app en los logs y en Actuator. Sin impacto funcional en JPA.
spring.application.name=testjpa

# ── Conexión a la base de datos ──────────────────────────────────────
# URL JDBC: jdbc:<dialecto>://<host>:<puerto>/<nombre_base_de_datos>
# Spring Boot detecta el dialecto MySQL automáticamente por el prefijo "jdbc:mysql"
spring.datasource.url=jdbc:mysql://localhost:3306/springapp

# Credenciales del usuario de BD. En producción usa variables de entorno:
# spring.datasource.username=${DB_USER}
spring.datasource.username=user
spring.datasource.password=1234

# ── Gestión del esquema (DDL) ─────────────────────────────────────────
# Controla si Hibernate crea, actualiza o valida las tablas al arrancar.
#
#   none        → Hibernate no toca el esquema. Tú lo gestionas externamente.
#   validate    → Solo comprueba que el esquema coincide con las entidades. Falla si no.
#   update      → Añade columnas/tablas nuevas. Nunca borra. Peligroso en producción.
#   create      → Borra y recrea las tablas al arrancar. Pierde datos en cada reinicio.
#   create-drop → Igual que create, pero además borra todo al parar la app.
#                 Útil para tests: cada ejecución empieza con un esquema limpio.
spring.jpa.hibernate.ddl-auto=create-drop

# ── Inicialización con SQL ────────────────────────────────────────────
# Si existe src/main/resources/data.sql, Spring lo ejecuta al arrancar.
# "always" → ejecuta el SQL siempre. "never" → no ejecuta nada.
# Útil para insertar datos de prueba junto con create-drop.
spring.sql.init.mode=always

# ── Logging del SQL generado ──────────────────────────────────────────
# Muestra en consola cada sentencia SQL que Hibernate envía a la BD.
# Imprescindible para depurar en desarrollo. Desactivar en producción.
spring.jpa.show-sql=true
⚠️
create-drop solo en desarrollo. Cada vez que arrancas la aplicación, Hibernate borra todas las tablas y las vuelve a crear desde cero. Pierdes todos los datos existentes. En producción usa siempre validate o none, gestionando el esquema con Flyway o Liquibase.

Entidades y mapeo de columnas

Una entidad JPA es una clase Java anotada con @Entity que se mapea a una tabla de la base de datos. Cada instancia de la entidad corresponde a una fila de esa tabla, y cada campo de la clase corresponde a una columna. Este proceso de traducción entre el mundo orientado a objetos y el mundo relacional se llama ORM (Object-Relational Mapping). JPA infiere los nombres de tabla y columna a partir del nombre de la clase y sus campos, pero puedes personalizarlos con anotaciones. Las anotaciones más importantes del mapeo son @Table para controlar la tabla, @Column para controlar cada columna (tipo, longitud, nulabilidad, unicidad), @Enumerated para enums, y @EntityListeners para habilitar funcionalidades como la auditoría automática de fechas.

Anatomía de una entidad completa

El siguiente ejemplo muestra una entidad real de producción con todas las anotaciones habituales comentadas. Los números ①–⑳ explican cada decisión de diseño.

model/Libro.java — entidad JPA completa y bien configuradaJava
@Entity                                           // ① marca la clase como entidad JPA
@Table(
    name = "libros",                               // ② nombre explícito de la tabla
    uniqueConstraints = @UniqueConstraint(          // ③ constraint UNIQUE compuesto
        name = "uk_libro_isbn",
        columnNames = {"isbn"}
    ),
    indexes = @Index(name = "idx_libro_titulo",    // ④ índice para búsquedas frecuentes
               columnList = "titulo")
)
@Getter @Setter
@NoArgsConstructor                                 // ⑤ obligatorio para JPA
@ToString(exclude = "autor")                       // ⑥ excluye relaciones de toString
@EqualsAndHashCode(onlyExplicitlyIncluded = true) // ⑦ solo el ID determina igualdad
@EntityListeners(AuditingEntityListener.class)   // ⑧ activa auditoría automática
public class Libro {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY) // ⑨ auto-increment BD
    @EqualsAndHashCode.Include                     // ⑩ solo el ID en equals/hashCode
    private Long id;

    @Column(nullable = false, length = 200)       // ⑪ NOT NULL, VARCHAR(200)
    private String titulo;

    @Column(unique = true, length = 13)           // ⑫ UNIQUE, VARCHAR(13)
    private String isbn;

    @Column(precision = 8, scale = 2)             // ⑬ DECIMAL(8,2) → hasta 999999.99
    private BigDecimal precio;

    @Column(nullable = false)
    private Integer stock = 0;                    // ⑭ valor por defecto en Java

    @Enumerated(EnumType.STRING)                  // ⑮ guarda "TECNICO", no 0/1/2
    @Column(nullable = false)
    private Genero genero;

    @Column(columnDefinition = "TEXT")            // ⑯ tipo TEXT de la BD
    private String descripcion;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "autor_id", nullable = false,
                foreignKey = @ForeignKey(name = "fk_libro_autor"))
    private Autor autor;                           // ⑰ FK con nombre explícito

    // ── Auditoría automática ──────────────────────────────────────
    @CreatedDate
    @Column(name = "creado_en", updatable = false) // ⑱ Spring rellena al crear
    private LocalDateTime creadoEn;

    @LastModifiedDate
    @Column(name = "modificado_en")               // ⑲ Spring actualiza en cada save
    private LocalDateTime modificadoEn;

    @CreatedBy
    @Column(name = "creado_por", updatable = false, length = 100)
    private String creadoPor;                      // ⑳ usuario que lo creó

    public enum Genero {
        FICCION, NO_FICCION, CIENCIA, HISTORIA, POESIA, INFANTIL, TECNICO
    }
}

Claves primarias — estrategias de generación

JPA puede generar el valor de la clave primaria automáticamente. La elección de la estrategia afecta al rendimiento en inserciones masivas y a la portabilidad entre bases de datos. IDENTITY delega en el autoincremento de la BD y es la más simple, pero obliga a ejecutar el INSERT antes de conocer el ID. SEQUENCE permite que Hibernate obtenga bloques de IDs de antemano (allocationSize), reduciendo drásticamente las llamadas a la BD en inserciones por lote. UUID es ideal en sistemas distribuidos donde múltiples nodos generan IDs sin coordinación, pero los índices UUID son más grandes y se fragmentan más que los numéricos.

IDENTITYSERIAL / AUTO_INCREMENTLa más común. MySQL, PostgreSQL⚠️ Necesita INSERT previo para obtener el ID
SEQUENCESecuencia de BDPostgreSQL, Oracle. Permite prefetch de IDs✅ Puede obtener N IDs de una sola llamada
UUIDUUID v4 aleatorioSistemas distribuidos, sin BD centralizada⚠️ Índices fragmentados, mayor tamaño
AUTODecide HibernateEvitar: comportamiento impredecible—
// IDENTITY (más común)
@Id @GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

// SEQUENCE con allocationSize (prefetch de 50 IDs → solo 1 llamada a la secuencia cada 50 inserciones)
@SequenceGenerator(name = "libro_seq", sequenceName = "seq_libros", allocationSize = 50)
@Id @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "libro_seq")
private Long id;

// UUID (JPA 3.1+ / Hibernate 6+)
@Id @GeneratedValue(strategy = GenerationType.UUID)
private UUID id;

Campos especiales: tipos, conversores y embebidos

JPA sabe persistir de forma nativa los tipos básicos de Java (String, Integer, BigDecimal, LocalDate…) pero no sabe qué hacer con tipos complejos como un Map<String, Object> o una clase de dominio propia. Para estos casos hay dos mecanismos complementarios: los conversores de atributo y las clases embebidas.

Conversores de atributo (@Convert)

Un conversor le dice a JPA cómo transformar un tipo Java en un tipo que la base de datos sí conoce, y viceversa. Implementa la interfaz AttributeConverter<TipoJava, TipoBD> con dos métodos: convertToDatabaseColumn (Java → BD al guardar) y convertToEntityAttribute (BD → Java al leer). Una vez definido el conversor, basta con anotar el campo con @Convert(converter = MiConverter.class).

En PostgreSQL, el tipo jsonb permite guardar JSON nativo con indexación. Mapearlo a un Map<String, Object> Java requiere un conversor que serialice/deserialice con Jackson. El atributo columnDefinition = "jsonb" le indica a Hibernate el tipo exacto de columna que debe crear en la BD.

// 1. Implementar el conversor (Jackson serializa/deserializa)
@Converter
public class JsonConverter implements AttributeConverter<Map<String, Object>, String> {
    private final ObjectMapper mapper = new ObjectMapper();

    @Override
    public String convertToDatabaseColumn(Map<String, Object> attr) {
        try { return mapper.writeValueAsString(attr); }  // Map → String JSON
        catch (Exception e) { throw new RuntimeException(e); }
    }

    @Override
    public Map<String, Object> convertToEntityAttribute(String dbData) {
        try { return mapper.readValue(dbData, Map.class); }  // String JSON → Map
        catch (Exception e) { throw new RuntimeException(e); }
    }
}

// 2. Usar el conversor en la entidad
@Convert(converter = JsonConverter.class)  // activa la conversión automática
@Column(columnDefinition = "jsonb")         // tipo exacto en PostgreSQL
private Map<String, Object> metadatos;      // en BD: {"clave":"valor"...}

Columnas con tipos nativos de la BD

Cuando la base de datos tiene un tipo sin equivalente JPA estándar (como los arrays de texto de PostgreSQL), puedes indicar el tipo literal con columnDefinition. Hibernate usará ese tipo tal cual al generar el DDL, aunque pierde portabilidad entre bases de datos.

// Array de Strings nativo de PostgreSQL (no es estándar JPA)
@Column(columnDefinition = "text[]")   // genera: etiquetas TEXT[] en el CREATE TABLE
private String[] etiquetas;            // Hibernate usa el driver para convertir

Clases embebidas (@Embeddable / @Embedded)

Una clase embebida agrupa campos que pertenecen al mismo concepto de dominio —como una dirección postal con calle, ciudad y código postal— en una clase Java separada, pero sin crear una tabla nueva. Todos sus campos se mapean como columnas de la tabla de la entidad propietaria.

Para usarla: anota la clase agrupada con @Embeddable y el campo de la entidad con @Embedded. Con @AttributeOverrides puedes renombrar las columnas generadas para que no colisionen ni sigan convenciones extrañas.

// 1. Definir la clase embebida (sin @Entity, sin @Id)
@Embeddable                          // marca la clase como embebible
public class Direccion {
    private String calle;
    private String ciudad;
    private String codigoPostal;
}
// Si se usa sin @AttributeOverrides, Hibernate genera columnas:
// "calle", "ciudad", "codigoPostal" en la tabla de la entidad propietaria

// 2. Embeber en la entidad propietaria y renombrar columnas
@Embedded
@AttributeOverrides({
    // @AttributeOverride(name = "<campo en Direccion>", column = @Column(name = "<nombre en BD>"))
    @AttributeOverride(name = "calle",        column = @Column(name = "dir_calle")),
    @AttributeOverride(name = "ciudad",       column = @Column(name = "dir_ciudad")),
    @AttributeOverride(name = "codigoPostal", column = @Column(name = "dir_cp"))
})
private Direccion direccion;
// Resultado en la BD: una sola tabla con columnas dir_calle, dir_ciudad, dir_cp
// No se crea ninguna tabla "direccion" separada

Relaciones entre entidades

JPA soporta los cuatro tipos de relaciones del modelo relacional. En toda relación bidireccional existe siempre un lado dueño y un lado inverso. El lado dueño es el que contiene la clave foránea en la base de datos y es quien realmente controla la relación: si modificas solo el lado inverso sin actualizar el lado dueño, Hibernate no guardará el cambio. El lado inverso se marca siempre con mappedBy apuntando al campo del lado dueño. Cada tipo de relación tiene implicaciones importantes en rendimiento, SQL generado y cómo se gestionan los objetos en memoria.

@ManyToOne — Muchos-a-uno (el más común)

Es la relación más usada en cualquier modelo de datos. El lado "muchos" (por ejemplo, Libro) guarda la clave foránea en su propia tabla como columna autor_id. Este es siempre el lado dueño de la relación. Siempre debe declararse con FetchType.LAZY: el valor por defecto de @ManyToOne es EAGER, lo que significa que cargar cualquier libro cargaría también su autor aunque no lo necesites.

// Libro.java (lado "muchos" — guarda la FK)
@ManyToOne(fetch = FetchType.LAZY)                // LAZY: no carga el Autor hasta que se acceda
@JoinColumn(
    name = "autor_id",                            // nombre de la columna FK en la tabla "libros"
    nullable = false,                              // la FK es NOT NULL
    foreignKey = @ForeignKey(name = "fk_libro_autor")  // nombre del constraint en la BD
)
private Autor autor;

@OneToMany — Uno-a-muchos

El lado "uno" (por ejemplo, Autor) es el lado inverso: no guarda la FK, solo declara la colección y usa mappedBy para indicar cuál es el campo dueño en la otra entidad. Como consecuencia, si añades un libro a la lista del autor pero no estableces libro.setAutor(autor), Hibernate no guardará la FK. Por eso la práctica estándar es añadir helper methods que mantengan ambos lados sincronizados. orphanRemoval = true hace que al eliminar un libro de la lista del autor, ese libro se borre también de la base de datos.

// Autor.java (lado "uno" — no guarda FK, usa mappedBy)
@OneToMany(
    mappedBy = "autor",                            // campo en Libro que tiene la FK
    cascade = CascadeType.ALL,                     // propaga save/delete a los libros
    fetch = FetchType.LAZY,                        // SIEMPRE LAZY en OneToMany
    orphanRemoval = true                            // si quitas un libro de la lista, se borra de la BD
)
@ToString.Exclude                                  // evita bucle infinito en toString()
private List<Libro> libros = new ArrayList<>();

// Helper methods para mantener la consistencia bidireccional:
public void addLibro(Libro libro) {
    libros.add(libro);
    libro.setAutor(this);   // mantener ambos lados sincronizados
}

public void removeLibro(Libro libro) {
    libros.remove(libro);
    libro.setAutor(null);
}

@ManyToMany — Muchos-a-muchos

En una relación muchos-a-muchos (por ejemplo, un Libro puede tener varias Etiquetas y una Etiqueta puede estar en varios libros), JPA necesita una tabla de unión intermedia para almacenar los pares de claves foráneas. El lado dueño define la tabla de unión con @JoinTable; el lado inverso solo usa mappedBy. Es recomendable usar Set en lugar de List porque evita duplicados y Hibernate lo gestiona de forma más eficiente.

// Libro.java (lado dueño de la relación)
@ManyToMany
@JoinTable(
    name = "libro_etiqueta",                       // nombre de la tabla de unión
    joinColumns        = @JoinColumn(name = "libro_id"),
    inverseJoinColumns = @JoinColumn(name = "etiqueta_id")
)
private Set<Etiqueta> etiquetas = new HashSet<>();  // Set evita duplicados

// Etiqueta.java (lado inverso)
@ManyToMany(mappedBy = "etiquetas")               // mappedBy: no guarda FK aquí
private Set<Libro> libros = new HashSet<>();

@OneToOne — Uno-a-uno

La relación uno-a-uno vincula exactamente una instancia de una entidad con exactamente una de otra. Se usa cuando los datos pertenecen conceptualmente juntos pero se benefician de estar en tablas separadas: por ejemplo, un Usuario y su Perfil (datos de uso frecuente vs. datos extendidos), o un Pedido y su Factura. La constraint unique = true en el @JoinColumn garantiza la unicidad a nivel de base de datos.

// Usuario tiene un Perfil (1:1)
@OneToOne(cascade = CascadeType.ALL, fetch = FetchType.LAZY)
@JoinColumn(name = "perfil_id", unique = true)    // unique: garantiza 1:1 en la BD
private Perfil perfil;

// Perfil.java (lado inverso, sin FK)
@OneToOne(mappedBy = "perfil")
private Usuario usuario;

Cascade — Propagación de operaciones

El cascade define si las operaciones de persistencia aplicadas a una entidad padre deben propagarse automáticamente a las entidades hijas asociadas. Sin cascade, guardar un Autor nuevo no guardaría sus Libros aunque estén en la lista; tendrías que persistirlos manualmente uno por uno. Con CascadeType.PERSIST, al guardar el padre se guardan los hijos. Con CascadeType.ALL, todas las operaciones (guardar, actualizar, borrar, refrescar, desconectar) se propagan. La regla práctica es usar ALL solo cuando la entidad hija no tiene sentido sin el padre y su ciclo de vida está completamente subordinado a él.

CascadeTypePropagaCuándo usarlo
PERSISTsave()Guardar hijos automáticamente al guardar el padre
MERGEmerge()Actualizar hijos al actualizar el padre
REMOVEdelete()Borrar hijos cuando se borra el padre
REFRESHrefresh()Recargar hijos desde la BD cuando se recarga el padre
DETACHdetach()Desconectar hijos del contexto de persistencia
ALLTodo lo anteriorEn relaciones padre-hijo donde el hijo no existe sin el padre
⚠️
Nunca uses CascadeType.REMOVE en relaciones @ManyToMany. Borrar un Libro borraría también todas las Etiquetas compartidas con otros libros. Úsalo solo en relaciones padre-hijo donde los hijos no existen sin el padre.

FetchType — Estrategia de carga

El FetchType controla cuándo Hibernate ejecuta la query para cargar una relación. Con EAGER, la relación se carga siempre al cargar la entidad padre, aunque no la necesites: Hibernate añade un JOIN o lanza una query adicional de forma automática e inevitable. Con LAZY, Hibernate crea un objeto proxy que parece la entidad pero no contiene datos reales; solo cuando accedes a uno de sus campos se ejecuta la query. El problema de EAGER es que acumula datos innecesarios y, cuando tienes varias relaciones EAGER encadenadas, el número de JOINs puede dispararse. Por eso la recomendación unánime de la comunidad JPA es usar siempre LAZY y cargar explícitamente las relaciones cuando se necesiten mediante JOIN FETCH en la query.

EAGER (default en @ManyToOne, @OneToOne)LAZY (default en @OneToMany, @ManyToMany)
Cuándo cargaAl cargar la entidad padreSolo cuando accedes a la colección/relación

Rendimiento⚠️ Puede cargar datos innecesarios✅ Solo carga lo que necesitas

💡
Regla de oro: usa FetchType.LAZY en todas las relaciones sin excepción. Cuando necesites los datos relacionados, usa JOIN FETCH en la query JPQL para cargarlos en una sola consulta.

Repository y consultas

Un repositorio es la capa que aísla el resto de la aplicación del acceso a la base de datos. Es el único lugar donde vive el código de persistencia: ni los services ni los controllers deben saber cómo se almacenan los datos. En Spring Data JPA, un repositorio es simplemente una interfaz Java — no una clase, no hay código que escribir. Spring genera en tiempo de arranque una implementación completa basada en los métodos que declares, la jerarquía que extiendas y las anotaciones @Query que añadas. El resultado es que en lugar de escribir consultas SQL o código de EntityManager, defines contratos en Java y Spring se encarga del resto.

Jerarquía de repositorios

Spring Data JPA organiza sus interfaces de repositorio en una jerarquía donde cada nivel añade más capacidades. Lo más habitual es extender directamente JpaRepository, que incluye todo lo que ofrecen los niveles anteriores más operaciones específicas de JPA como flush, operaciones en lote y la búsqueda por referencia. Si además necesitas búsquedas dinámicas con criterios variables, implementa también JpaSpecificationExecutor, que añade el método findAll(Specification) sin herencia múltiple ya que es una interfaz independiente.

InterfazExtiendeAñade
Repository—Interfaz marcador vacía
CrudRepositoryRepositorysave, findById, findAll, delete, count
PagingAndSortingRepositoryCrudRepositoryfindAll(Pageable), findAll(Sort)
JpaRepositoryPagingAndSortingRepositorysaveAll, deleteInBatch, flush, getById…
JpaSpecificationExecutor—findAll(Specification) para búsquedas dinámicas

Métodos derivados del nombre

Spring Data analiza el nombre del método y genera automáticamente la query JPQL correspondiente. El nombre sigue la sintaxis findBy + campo + condición. Los campos de relaciones se navegan con guión bajo (_): findByAutor_Nombre genera un JOIN a la tabla de autores y filtra por nombre. Las palabras clave disponibles incluyen Is, Not, Between, LessThan, GreaterThan, Like, Containing, StartingWith, EndingWith, IgnoreCase, IsNull, IsNotNull, In, OrderBy, Top/First y Distinct. Son ideales para queries simples y frecuentes; cuando la query es compleja o necesita parámetros opcionales, usa @Query o Specifications.

public interface LibroRepository extends JpaRepository<Libro, Long>,
                                                JpaSpecificationExecutor<Libro> {

    // Búsquedas simples
    Optional<Libro> findByIsbn(String isbn);
    boolean           existsByIsbn(String isbn);
    List<Libro>      findByGenero(Libro.Genero genero);

    // Comparaciones numéricas
    List<Libro> findByPrecioLessThan(BigDecimal max);
    List<Libro> findByPrecioBetween(BigDecimal min, BigDecimal max);
    List<Libro> findByStockGreaterThan(Integer minStock);

    // Strings: Like, IgnoreCase, StartingWith, EndingWith, Containing
    List<Libro> findByTituloContainingIgnoreCase(String texto);
    List<Libro> findByTituloStartingWith(String prefijo);

    // Nulo y no nulo
    List<Libro> findByIsbnIsNull();
    List<Libro> findByIsbnIsNotNull();

    // Relaciones: navegar con _ (guión bajo)
    List<Libro> findByAutor_Nombre(String nombreAutor);     // JOIN a Autor
    List<Libro> findByAutor_Nacionalidad(String pais);

    // Ordenación
    List<Libro> findByGeneroOrderByPrecioAsc(Libro.Genero genero);
    List<Libro> findTop5ByOrderByStockDesc();              // los 5 con más stock

    // Paginación y ordenación
    Page<Libro> findByGenero(Libro.Genero genero, Pageable pageable);

    // Contar y existir
    long countByGenero(Libro.Genero genero);
    boolean existsByTituloAndAutor_Id(String titulo, Long autorId);
}

Queries JPQL con @Query

JPQL (Jakarta Persistence Query Language) es un lenguaje de consulta orientado a objetos que opera sobre entidades y sus atributos en lugar de tablas y columnas. Esto lo hace portable entre bases de datos: la misma query JPQL funciona en PostgreSQL, MySQL u Oracle sin cambios. Spring Data la convierte al SQL específico del dialecto configurado en tiempo de arranque. Cuando JPQL no es suficiente (funciones específicas de la BD, full-text search, consultas muy complejas), puedes usar SQL nativo con nativeQuery = true, sacrificando la portabilidad a cambio de acceso completo a las capacidades de la base de datos. Las queries marcadas con @Modifying (UPDATE/DELETE) deben ejecutarse siempre dentro de una transacción activa y evitan cargar las entidades en memoria, siendo mucho más eficientes para actualizaciones masivas.

// JPQL con JOIN FETCH: carga la relación en UNA sola query (evita N+1)
@Query("""
    SELECT l FROM Libro l
    JOIN FETCH l.autor a
    WHERE (:titulo IS NULL OR LOWER(l.titulo) LIKE LOWER(CONCAT('%',:titulo,'%')))
      AND (:genero IS NULL OR l.genero = :genero)
      AND (:autorNombre IS NULL OR LOWER(a.nombre) LIKE LOWER(CONCAT('%',:autorNombre,'%')))
    ORDER BY l.titulo
    """)
Page<Libro> buscar(
    @Param("titulo")      String titulo,
    @Param("genero")      Libro.Genero genero,
    @Param("autorNombre") String autorNombre,
    Pageable pageable
);

// Query nativa SQL (usa funciones específicas de PostgreSQL)
@Query(value = """
    SELECT l.*, ts_rank(to_tsvector('spanish', l.titulo || ' ' || l.descripcion),
                        plainto_tsquery('spanish', :texto)) AS rank
    FROM libros l
    WHERE to_tsvector('spanish', l.titulo || ' ' || l.descripcion)
          @@ plainto_tsquery('spanish', :texto)
    ORDER BY rank DESC
    LIMIT :limit
    """,
    nativeQuery = true)
List<Libro> buscarFullText(@Param("texto") String texto, @Param("limit") int limit);

// UPDATE directo (no carga la entidad en memoria → más eficiente)
@Modifying
@Query("UPDATE Libro l SET l.stock = l.stock - :cantidad WHERE l.id = :id AND l.stock >= :cantidad")
int decrementarStock(@Param("id") Long id, @Param("cantidad") Integer cantidad);

// DELETE directo
@Modifying
@Query("DELETE FROM Libro l WHERE l.stock = 0 AND l.modificadoEn < :fecha")
int eliminarSinStock(@Param("fecha") LocalDateTime fecha);

Especificaciones — búsquedas dinámicas

Los métodos derivados del nombre son ideales para queries fijas, pero no para búsquedas donde los criterios son opcionales y variables. Si el usuario puede filtrar por título, género y precio en cualquier combinación, necesitarías un método distinto por cada combinación posible. Las Specifications resuelven esto: cada criterio de filtrado se encapsula en un método independiente, y luego se componen con and() y or() para construir la query dinámicamente.

Una Specification<T> es una función lambda con tres parámetros que Spring JPA pasa automáticamente:

  • root — representa la entidad raíz de la query (en este caso Libro). Con root.get("titulo") accedes a la columna titulo de la tabla de libros, de forma tipada y sin strings SQL.
  • query — el objeto de query en construcción. Permite añadir ORDER BY, DISTINCT o sub-queries. En la mayoría de casos no se usa directamente.
  • cb (CriteriaBuilder) — la fábrica de condiciones. Con él construyes predicados como cb.like() (contiene texto), cb.equal() (igualdad exacta), cb.lessThanOrEqualTo() (comparación numérica), etc. Si la Specification devuelve null, Spring ignora ese criterio completamente y no añade nada al WHERE.
public class LibroSpec {

    // Criterio de título: busca libros cuyo título CONTENGA el texto (case-insensitive)
    // Si titulo es null → devuelve null → Spring omite esta condición del WHERE
    public static Specification<Libro> conTitulo(String titulo) {
        return (root, query, cb) -> titulo == null ? null
            : cb.like(
                cb.lower(root.get("titulo")),    // cb.lower: pasa la columna a minúsculas
                "%" + titulo.toLowerCase() + "%"  // % = comodín SQL para "contiene"
              );
    }

    // Criterio de género: busca libros de un género EXACTO
    // cb.equal genera: WHERE l.genero = ?
    public static Specification<Libro> conGenero(Libro.Genero genero) {
        return (root, query, cb) -> genero == null ? null
            : cb.equal(root.get("genero"), genero);
            // root.get("genero") → columna genero de la tabla libros
    }

    // Criterio de precio: busca libros con precio ≤ max
    // cb.lessThanOrEqualTo genera: WHERE l.precio <= ?
    public static Specification<Libro> conPrecioMenorQue(BigDecimal max) {
        return (root, query, cb) -> max == null ? null
            : cb.lessThanOrEqualTo(root.get("precio"), max);
    }
}
// Spring evalúa SOLO los criterios que no son null.
// Ejemplos de SQL generado según lo que pase el usuario:
//   titulo="clean", genero=null, precioMax=null → WHERE LOWER(titulo) LIKE '%clean%'
//   titulo=null,    genero=TECNICO, precioMax=50 → WHERE genero='TECNICO' AND precio <= 50
//   titulo="java",  genero=TECNICO, precioMax=30 → WHERE LOWER(titulo) LIKE '%java%'
//                                                    AND genero='TECNICO' AND precio <= 30
public Page<LibroResponseDTO> buscar(FiltroBusqueda filtro, Pageable p) {
    Specification<Libro> spec = Specification
        .where(LibroSpec.conTitulo(filtro.titulo()))       // puede ser null → se omite
        .and(LibroSpec.conGenero(filtro.genero()))         // puede ser null → se omite
        .and(LibroSpec.conPrecioMenorQue(filtro.precioMax()));

    // repo.findAll(spec, p) ejecuta la query con solo las condiciones activas
    // + aplica la paginación y ordenación del Pageable
    return repo.findAll(spec, p).map(mapper::toResponse);
}

Proyecciones — recuperar solo los campos necesarios

Cuando un endpoint solo necesita mostrar el título y el precio de un libro, cargar la entidad Libro completa (con todos sus campos, relaciones lazy y overhead de Hibernate) es un desperdicio. Las proyecciones permiten indicarle a Spring Data exactamente qué columnas recuperar, generando un SELECT más estrecho y eficiente que nunca toca la entidad.

Hay dos estilos. Las proyecciones de interfaz definen una interfaz con getters; Spring genera automáticamente un proxy dinámico que implementa esa interfaz mapeando cada getter al alias correspondiente de la query. Las proyecciones DTO con record usan la sintaxis new de JPQL para construir directamente el objeto Java; son más explícitas, refactorizables y no dependen de proxies.

// 1. Definir la interfaz de proyección (solo con los campos que necesitas)
public interface LibroResumen {
    Long       getId();
    String     getTitulo();
    BigDecimal getPrecio();
}

// 2. Usarla en el repositorio: Spring genera SELECT id, titulo, precio FROM libros
//    El alias en JPQL (AS id, AS titulo…) debe coincidir con el nombre del getter sin get
@Query("SELECT l.id AS id, l.titulo AS titulo, l.precio AS precio FROM Libro l WHERE l.genero = :g")
List<LibroResumen> findResumenByGenero(@Param("g") Libro.Genero g);
// 1. Definir el record DTO (inmutable, sin boilerplate)
public record LibroTituloDTO(Long id, String titulo) {}

// 2. Usar new en JPQL para construir el record directamente
//    Spring no crea un proxy, construye el record con su constructor canónico
//    El orden de los argumentos debe coincidir con el del constructor del record
@Query("SELECT new com.ejemplo.dto.LibroTituloDTO(l.id, l.titulo) FROM Libro l WHERE l.stock > 0")
List<LibroTituloDTO> findTitulosDisponibles();
💡
Usa proyecciones en todos los endpoints de listado o búsqueda que no necesiten la entidad completa para operar. Son especialmente útiles en listas paginadas con muchos resultados: reducen el volumen de datos transferidos de la BD y eliminan el riesgo de accidentalmente disparar relaciones lazy.
17 · JPA / Persistencia

Transacciones

Una transacción es una unidad de trabajo atómica: o todas las operaciones se completan correctamente (commit), o ninguna se aplica (rollback). Spring gestiona las transacciones de forma declarativa con @Transactional.

@Transactional — todos sus parámetros

@Transactional acepta varios parámetros que controlan el comportamiento de la transacción. El más importante en el día a día es readOnly = true: cuando se activa, Hibernate desactiva el dirty-checking (no compara el estado inicial y final de cada entidad para detectar cambios), no hace flush automático, y la base de datos puede optimizar la ejecución de la query. En un servicio con muchos métodos de lectura, declarar @Transactional(readOnly = true) a nivel de clase y sobreescribir con @Transactional (sin readOnly) solo en los métodos de escritura es el patrón más limpio y eficiente.

ParámetroDefaultDescripción
readOnlyfalseOptimiza para lectura: sin dirty-checking, sin flush. Siempre en métodos de solo lectura
propagationREQUIREDCómo se comporta respecto a transacciones existentes (ver tabla debajo)
isolationDEFAULTNivel de aislamiento entre transacciones concurrentes
rollbackForRuntimeExceptionClases de excepción que provocan rollback (incluir checked si necesario)
noRollbackFor—Excepciones que NO deben provocar rollback
timeout-1 (sin límite)Segundos máximos antes de hacer rollback automático

Propagation — comportamiento ante transacciones existentes

La propagación define qué sucede cuando un método transaccional llama a otro método transaccional. El caso más habitual es REQUIRED (el default): si ya hay una transacción activa, el método se une a ella y comparten el mismo contexto; si no hay ninguna, se crea una nueva. El caso más importante tras REQUIRED es REQUIRES_NEW: siempre abre una transacción nueva, suspendiendo la actual si existía. Esto es imprescindible para operaciones que deben persistirse independientemente del resultado del llamador, como el registro de auditoría: si el proceso principal falla y hace rollback, el log de auditoría ya está guardado en su propia transacción completada.

@Service
@RequiredArgsConstructor
@Transactional                              // TX por defecto para todos los métodos
public class PedidoService {

    // ① Escritura normal: usa la TX de la clase
    public Pedido crear(PedidoDTO dto) {
        verificarStock(dto.getItems());
        Pedido pedido = repo.save(mapper.toEntity(dto));
        // Si verificarStock() lanza excepción → rollback automático
        return pedido;
    }

    // ② Solo lectura: optimización importante
    @Transactional(readOnly = true)
    public Page<PedidoDTO> listar(Pageable p) { return repo.findAll(p).map(mapper::toDTO); }

    // ③ TX independiente: el log de auditoría se guarda aunque falle el pedido
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void registrarAuditoria(AuditoriaDTO dto) {
        auditoriaRepo.save(mapper.toAuditoria(dto));
    }

    // ④ Con rollbackFor para checked exceptions
    @Transactional(rollbackFor = IOException.class)
    public void exportar(Long id) throws IOException {
        Pedido p = repo.findById(id).orElseThrow();
        archivoService.escribir(p);           // IOException es checked → necesita rollbackFor
    }

    // ⑤ Timeout: la TX no puede durar más de 30 segundos
    @Transactional(timeout = 30)
    public void procesarLote(List<PedidoDTO> dtos) {
        dtos.forEach(this::crear);
    }
}

Isolation — niveles de aislamiento

El nivel de aislamiento controla hasta qué punto una transacción está aislada de los cambios que otras transacciones concurrentes están realizando en la misma BD. Un mayor aislamiento garantiza más consistencia pero reduce el rendimiento porque exige más bloqueos. Los tres fenómenos que el aislamiento previene son: el dirty read (leer datos que otra transacción aún no ha confirmado y podría revertir), el non-repeatable read (la misma fila devuelve valores distintos en dos lecturas de la misma TX porque otra TX la actualizó entre medias), y el phantom read (el número de filas que cumplen un criterio cambia entre dos lecturas de la misma TX porque otra TX insertó o borró filas).

NivelDirty ReadNon-Repeatable ReadPhantom ReadRendimiento
READ_UNCOMMITTED✅ posible✅ posible✅ posibleMáximo
READ_COMMITTED❌ no✅ posible✅ posibleAlto
REPEATABLE_READ❌ no❌ no✅ posibleMedio
SERIALIZABLE❌ no❌ no❌ noMínimo

PostgreSQL usa READ_COMMITTED por defecto, que es suficiente para la mayoría de casos. Solo sube el nivel cuando tengas problemas de concurrencia demostrados.

Rendimiento y optimización

El problema N+1 — el error más común con JPA

El problema N+1 ocurre cuando cargas N entidades y accedes a su relación lazy: JPA lanza 1 query para los N libros, y luego N queries adicionales, una por cada libro para cargar su autor. Si tienes 1000 libros, son 1001 queries.

// ❌ N+1 QUERIES: 1 query para libros + 1 query por cada libro para el autor
List<Libro> libros = repo.findAll();      // SELECT * FROM libros → 1 query
libros.forEach(l ->
    log.info("Autor: {}", l.getAutor().getNombre())  // SELECT * FROM autores WHERE id=? → N queries
);
// Si hay 100 libros: 101 queries a la BD
// ✅ SOLUCIÓN 1: JOIN FETCH en la query → 1 sola query
@Query("SELECT l FROM Libro l JOIN FETCH l.autor")
List<Libro> findAllConAutor();

// ✅ SOLUCIÓN 2: @EntityGraph → Spring genera el JOIN FETCH automáticamente
@EntityGraph(attributePaths = {"autor", "etiquetas"})  // carga autor y etiquetas de golpe
@Query("SELECT l FROM Libro l")
List<Libro> findAllConRelaciones();

// ✅ SOLUCIÓN 3: default_batch_fetch_size en application.yml
// En lugar de N queries individuales, hace SELECT * FROM autores WHERE id IN (1,2,3,...,25)
// spring.jpa.properties.hibernate.default_batch_fetch_size=25
// No requiere cambios en el código, solo configuración

// ✅ SOLUCIÓN 4: Proyección DTO → no carga entidades, evita el problema totalmente
@Query("SELECT new com.ej.dto.LibroDTO(l.id, l.titulo, a.nombre) FROM Libro l JOIN l.autor a")
List<LibroDTO> findLibrosDTO();

Detección de N+1: Hibernate Statistics

Diagnosticar el problema N+1 manualmente leyendo los logs de SQL es tedioso. Hibernate tiene un sistema de estadísticas que al finalizar cada transacción imprime un resumen completo: cuántas queries se ejecutaron, cuántas filas se procesaron, tiempos y hits de caché. Activar estas estadísticas en desarrollo y combinarlas con el log de queries lentas te permite identificar exactamente qué métodos están disparando demasiadas queries antes de que el problema llegue a producción.

spring:
  jpa:
    properties:
      hibernate:
        generate_statistics: true   # muestra stats al final de cada TX
        session:
          events:
            log:
              LOG_QUERIES_SLOWER_THAN_MS: 25  # loguear queries lentas

logging:
  level:
    org.hibernate.stat: DEBUG        # muestra "N queries executed"
    org.hibernate.SQL: DEBUG         # muestra el SQL generado
    org.hibernate.type.descriptor.sql: TRACE  # muestra los parámetros

Inserción masiva — batch inserts

Cuando necesitas guardar miles de entidades de una vez (importaciones de datos, migraciones, procesamiento por lotes), hacer un save() individual por cada entidad genera una query SQL separada por elemento: 10.000 registros producen 10.000 INSERTs independientes, lo cual es extremadamente lento. Hibernate puede agrupar esos INSERTs en lotes (batches) y enviarlos juntos al servidor de BD en una sola llamada de red. Sin embargo, hay que gestionar activamente el contexto de persistencia: si acumulas 10.000 entidades en memoria sin hacer flush() y clear(), la memoria del proceso se agota porque Hibernate rastrea el estado de cada objeto. La solución es hacer flush y clear cada N elementos (25 o 50 suele ser un buen tamaño) para vaciar el contexto y liberar memoria periódicamente.

// Configurar batch en application.yml:
// spring.jpa.properties.hibernate.jdbc.batch_size=25
// spring.jpa.properties.hibernate.order_inserts=true

// En el service: flush + clear periódico para no agotar la memoria
@Transactional
public void importarLibros(List<LibroCSV> datos) {
    for (int i = 0; i < datos.size(); i++) {
        libroRepo.save(mapper.toEntity(datos.get(i)));

        if (i % 25 == 0) {         // cada 25 elementos
            em.flush();              // fuerza el envío del lote a la BD
            em.clear();              // libera la memoria del contexto de persistencia
        }
    }
}

Caché de segundo nivel

Hibernate mantiene dos niveles de caché. El caché de primer nivel es el propio contexto de persistencia: vive dentro de una transacción y se descarta al terminarla. Es automático e inevitable. El caché de segundo nivel es compartido entre todas las transacciones y sesiones de la aplicación: si una sesión carga la entidad Categoria(id=5), la segunda sesión que la pida la obtendrá de caché sin ir a la BD. Es especialmente útil para entidades de referencia que se leen con mucha frecuencia pero cambian raramente: países, categorías, tipos de moneda, configuraciones de sistema. Para entidades que cambian con frecuencia, el caché de segundo nivel añade complejidad sin beneficio. La estrategia de concurrencia más segura para datos que ocasionalmente se actualizan es READ_WRITE; para datos que nunca cambian en producción, IMMUTABLE es más eficiente.

// 1. Añadir dependencia: spring-boot-starter-cache + ehcache o caffeine
// 2. Activar en application.yml:
//    hibernate.cache.use_second_level_cache: true
//    hibernate.cache.region.factory_class: JCacheRegionFactory

// 3. Anotar la entidad como cacheable
@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)  // estrategia de concurrencia
public class Categoria {                              // pocas categorías que cambian poco
    ...
}

// También funciona a nivel de query:
@QueryHints(@QueryHint(name = HINT_CACHEABLE, value = "true"))
List<Categoria> findAll();

¿Qué es REST?

REST (Representational State Transfer) es un estilo arquitectónico para sistemas distribuidos definido por Roy Fielding en su tesis doctoral en el año 2000. No es un protocolo ni un estándar, sino un conjunto de restricciones de diseño.

Un sistema que sigue todas estas restricciones se denomina RESTful.

Los 6 principios REST

1
Interfaz uniforme

Todos los recursos se identifican con URIs. La interacción con cualquier recurso sigue siempre el mismo contrato: método HTTP + URI + representación. Esto desacopla al cliente del servidor.

2
Sin estado (Stateless)

Cada petición HTTP contiene toda la información necesaria para procesarla. El servidor no guarda ningún contexto de sesión entre peticiones. El estado de la aplicación (autenticación, etc.) viaja en cada petición (JWT, cabeceras).

3
Caché

Las respuestas deben indicar si pueden cachearse. Reducen la carga en el servidor y mejoran la latencia del cliente. Se controla con las cabeceras HTTP Cache-Control, ETag y Last-Modified.

4
Sistema en capas

El cliente no sabe si se conecta directamente al servidor final o a un intermediario (proxy, load balancer, API gateway). Cada capa solo conoce a la capa adyacente.

5
Código bajo demanda (opcional)

El servidor puede enviar código ejecutable al cliente (JavaScript, applets). Este principio es opcional y raramente se usa en APIs REST modernas.

6
Arquitectura cliente-servidor

La UI y el almacenamiento de datos están desacoplados. El servidor no sabe nada del cliente. Esto permite que evolucionen de forma independiente.

Recursos y URIs

En REST, un recurso es cualquier cosa que tenga identidad propia: un libro, un usuario, un pedido, una colección de libros. Cada recurso se identifica con una URI (Uniform Resource Identifier) única y estable. La URI es la dirección pública del recurso y debe diseñarse para que sea legible, predecible y coherente. Un buen diseño de URIs es la primera señal de calidad de una API.

Reglas de diseño de URIs

Estas reglas no son arbitrarias: representan convenciones adoptadas por la industria que hacen las APIs predecibles y fáciles de consumir. La más importante es usar sustantivos en plural para las colecciones (porque la URI identifica el recurso, no la acción) y evitar verbos (porque la acción ya la indica el método HTTP: GET, POST, DELETE…).

ReglaCorrecto ✅Incorrecto ❌
Sustantivos en plural para colecciones/libros/libro, /getLibros
Minúsculas y guiones para espacios/autores-famosos/AutoresFamosos
IDs para recursos individuales/libros/42/libros?id=42
Relaciones como sub-recursos/autores/3/libros/librosPorAutor/3
Sin verbos en la URIDELETE /libros/42POST /eliminarLibro/42
Sin extensión de archivo/libros/42/libros/42.json
Versionado en el path o header/api/v1/libros/libros_v1

Jerarquía de recursos

Los recursos que tienen una relación de pertenencia se expresan como sub-recursos anidando la URI hija bajo la URI padre. Un libro pertenece a un autor, por lo que /autores/7/libros es más semántico que /libros?autorId=7. Sin embargo, el anidamiento tiene un límite práctico: más de dos niveles de profundidad hace las URIs difíciles de leer y mantener.

Ejemplos de URIs bien diseñadasURI

GET  /api/v1/libros?genero=TECNICO   ← colección filtrada (query params)
GET  /api/v1/libros/42               ← recurso individual
GET  /api/v1/libros/42/resenas       ← sub-recurso: reseñas del libro 42
GET  /api/v1/autores/7/libros        ← sub-recurso: libros del autor 7
POST /api/v1/libros/42/resenas       ← crear una reseña del libro 42
⚠️
Evita anidar recursos más de dos niveles. /autores/7/libros/42/resenas es difícil de mantener. Si la sub-ruta crece, considera aplanarla: /resenas?libroId=42.

Códigos de estado HTTP

El código de estado es la forma principal que tiene el servidor de comunicar el resultado de la operación al cliente. Están agrupados en cinco familias por su primer dígito: 1xx informativo, 2xx éxito, 3xx redirección, 4xx error del cliente y 5xx error del servidor. Usar los códigos correctos es fundamental: devolver siempre 200 aunque haya errores (práctica común en APIs mal diseñadas) impide que los clientes distingan el éxito del fallo sin leer el body.

2xx — Éxito

Indican que la petición fue recibida, entendida y procesada correctamente. La elección entre 200, 201 y 204 no es opcional: cada uno tiene una semántica precisa que el cliente puede interpretar sin leer el body.

Indican que el cliente debe tomar alguna acción adicional para completar la petición, normalmente seguir una nueva URL. Son poco frecuentes en APIs REST puras.

CódigoNombreCuándo usarlo

Nunca devuelvas 404 donde debería ir un 403 para ocultar la existencia de un recurso, ya que esto confunde a los clientes legítimos.

Negociación de contenido

La negociación de contenido es el mecanismo por el cual el cliente y el servidor acuerdan el formato de los datos intercambiados sin que la URI cambie. El cliente anuncia en la cabecera Accept qué formatos puede procesar (por ejemplo, JSON o XML), y el servidor responde con el que mejor se ajusta, informando del formato elegido mediante Content-Type en la respuesta. Si el servidor no puede ofrecer ninguno de los formatos solicitados, devuelve 406 Not Acceptable. Spring Boot negocia JSON automáticamente cuando Jackson está en el classpath, sin necesitar ninguna configuración adicional.

Leonard Richardson propuso un modelo de 4 niveles para clasificar el grado de "RESTfulness" de una API. La mayoría de APIs industriales se quedan en el nivel 2.

0
Nivel 0 — El pantano del POX

Una sola URI para todo. El método HTTP no importa. La acción va en el body. Es básicamente RPC (Remote Procedure Call) sobre HTTP. Ejemplo: POST /api?action=getLibro&id=42

1
Nivel 1 — Recursos

URIs distintas para cada recurso, pero todavía se usa un solo método HTTP (normalmente POST para todo). Ejemplo: POST /libros/42 para leer, crear y borrar.

2
Nivel 2 — Verbos HTTP ⭐ El estándar de la industria

Cada operación usa el método HTTP correcto (GET, POST, PUT, DELETE) y los códigos de estado apropiados. Es el nivel que implementan la mayoría de APIs REST modernas.

3
Nivel 3 — HATEOAS (Hypermedia)

Las respuestas incluyen enlaces (_links) que guían al cliente sobre qué puede hacer a continuación. El cliente no necesita conocer las URIs de antemano. Es la definición "pura" de REST pero pocas APIs lo implementan.

25 · Teoría REST

Buenas prácticas de diseño

Un API REST bien diseñado es predecible, consistente y evoluciona sin romper a los clientes existentes. Estas prácticas no son requisitos técnicos del protocolo HTTP, sino convenciones adoptadas por la industria que hacen que cualquier desarrollador pueda entender y consumir tu API sin necesidad de leer toda la documentación de antemano.

📦
Versiona tu API
Prefija todas las rutas con /api/v1/. Cuando hagas cambios incompatibles, crea /api/v2/. Nunca rompas clientes existentes.
🔒
Usa DTOs, no entidades
Nunca expongas tus entidades JPA directamente. Los DTOs controlan qué campos entran y salen y evitan referencias circulares.
✅
Valida siempre la entrada
Usa Bean Validation (@NotBlank, @Valid…) en tus DTOs de entrada. Nunca confíes en los datos del cliente.
🚨
Errores consistentes
Define un formato de error único para toda la API y aplícalo con @RestControllerAdvice. Incluye código, mensaje y timestamp.
📄
Pagina las colecciones
Nunca devuelvas listas sin límite. Usa Page<T> de Spring Data con parámetros page, size y sort.
📖
Documenta con OpenAPI
Usa springdoc-openapi para generar la documentación automáticamente. Enriquece con @Operation, @Schema y @ApiResponse.

Reglas de oro de un API REST

  • Usa sustantivos en las URIs, nunca verbos: /libros, no /obtenerLibros
  • El método HTTP es el verbo: DELETE /libros/42, no POST /eliminarLibro/42
  • Devuelve siempre el código de estado HTTP correcto: 201 al crear, 204 al borrar sin body
  • Incluye el header Location con la URL del nuevo recurso en las respuestas 201
  • En errores de validación (400), detalla qué campo falla y por qué
  • No expongas información interna del servidor en los errores 500
  • Usa HTTPS en producción siempre, sin excepciones
  • Implementa rate limiting para proteger la API de abusos

Controllers y mapeos

En Spring MVC, un controller REST es una clase anotada con @RestController, que combina @Controller (registro del bean en el contexto Spring) con @ResponseBody (serialización automática de los objetos devueltos a JSON mediante Jackson). Cada método público del controller se mapea a una petición HTTP concreta mediante anotaciones como @GetMapping, @PostMapping, etc. El controller no debe contener lógica de negocio: su única responsabilidad es transformar la petición HTTP en una llamada al servicio y transformar la respuesta del servicio en una respuesta HTTP.

El siguiente ejemplo muestra la anatomía completa de un controller REST con los 13 elementos comentados. Fíjate especialmente en ⑨ la construcción del header Location al crear (obligatorio en respuestas 201), y en ⑬ el 204 sin body al borrar.

28 · Spring MVC REST

DTOs y validación

Los DTOs (Data Transfer Objects) son los objetos que forman el contrato público de tu API. Son clases Java planas —generalmente Records— que definen exactamente qué campos viajan hacia dentro y hacia fuera del sistema. La separación entre DTOs de entrada (Request) y de salida (Response) es deliberada: un DTO de entrada lleva anotaciones de validación Bean Validation (@NotBlank, @Valid…) y Spring las ejecuta automáticamente antes de que el método del controller se invoque; un DTO de salida solo lleva anotaciones de serialización (@JsonFormat) y no necesita validarse. Usar DTOs en lugar de entidades JPA directamente es una práctica fundamental por tres razones:

  • Controlas exactamente qué datos expones — nunca se filtran campos internos como contraseñas o columnas de auditoría
  • Las validaciones de la API no contaminan el modelo de dominio ni las reglas de negocio del service
  • Evitas referencias circulares de JPA que romperían la serialización JSON (por ejemplo, Autor → libros → autor → …)

El patrón más limpio es tener un DTO de entrada por operación de escritura y un único DTO de salida que se reutiliza en todos los endpoints de lectura. Cualquier transformación entre DTO y entidad va en una clase Mapper separada.

29 · Spring MVC REST

ResponseEntity

ResponseEntity<T> es el contenedor que Spring MVC usa para representar una respuesta HTTP completa: código de estado, cabeceras y body. Si un método del controller devuelve directamente un objeto Java (por ejemplo, LibroDTO), Spring lo serializa a JSON con código 200 y sin cabeceras adicionales. Eso es suficiente para los casos simples, pero hay situaciones donde necesitas control explícito: al crear un recurso debes devolver 201 más el header Location, al borrar debes devolver 204 sin body, o puede que el resultado sea condicional (el recurso existe → 200, no existe → 404). En todos esos casos, ResponseEntity es la herramienta correcta. Su API de construcción es fluida y legible: ResponseEntity.ok(dto), ResponseEntity.created(uri).body(dto), ResponseEntity.noContent().build().

Patrones de uso de ResponseEntityJava
// 200 OK con body
return ResponseEntity.ok(dto);

// 201 Created con header Location (obligatorio al crear recursos)
URI location = ServletUriComponentsBuilder
    .fromCurrentRequest().path("/{id}")
    .buildAndExpand(creado.id()).toUri();
return ResponseEntity.created(location).body(creado);

// 204 No Content (sin body)
return ResponseEntity.noContent().build();

// 200 condicional: recurso encontrado o 404
return repo.findById(id)
    .map(ResponseEntity::ok)
    .orElse(ResponseEntity.notFound().build());

// Con cabeceras personalizadas
return ResponseEntity.ok()
    .header("X-Total-Count", String.valueOf(total))
    .header("Cache-Control", "max-age=3600")
    .body(lista);

Manejo global de errores

Un API bien diseñado devuelve errores con un formato siempre consistente. En Spring, el lugar correcto para centralizar esto es una clase anotada con @RestControllerAdvice.

public record ApiError(

Handler global

exception/GlobalExceptionHandler.javaJava
@RestControllerAdvice    // aplica a todos los @RestController de la app
@Slf4j
public class GlobalExceptionHandler {

    // ── 404 ─────────────────────────────────────────────────────────
    @ExceptionHandler(LibroNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ApiError handleNotFound(LibroNotFoundException ex) {
        return ApiError.of("NOT_FOUND", ex.getMessage());
    }

    // ── 400 Validación ───────────────────────────────────────────────
    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ApiError handleValidation(MethodArgumentNotValidException ex) {
        List<String> detalles = ex.getBindingResult().getFieldErrors().stream()
            .sorted(Comparator.comparing(FieldError::getField))
            .map(e -> e.getField() + ": " + e.getDefaultMessage())
            .toList();
        return ApiError.withDetails("VALIDATION_ERROR", "Datos de entrada inválidos", detalles);
    }

    // ── 400 Tipo incorrecto en parámetro ─────────────────────────────
    @ExceptionHandler(MethodArgumentTypeMismatchException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ApiError handleTypeMismatch(MethodArgumentTypeMismatchException ex) {
        String msg = "Parámetro '%s' con valor inválido: '%s'"
            .formatted(ex.getName(), ex.getValue());
        return ApiError.of("BAD_PARAMETER", msg);
    }

    // ── 409 Conflicto (e.g. ISBN duplicado) ──────────────────────────
    @ExceptionHandler(RecursoYaExisteException.class)
    @ResponseStatus(HttpStatus.CONFLICT)
    public ApiError handleConflict(RecursoYaExisteException ex) {
        return ApiError.of("CONFLICT", ex.getMessage());
    }

    // ── 400 JSON mal formado ─────────────────────────────────────────
    @ExceptionHandler(HttpMessageNotReadableException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ApiError handleMalformedJson(HttpMessageNotReadableException ex) {
        return ApiError.of("MALFORMED_JSON", "El cuerpo de la petición no es JSON válido");
    }

    // ── 500 Genérico ─────────────────────────────────────────────────
    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public ApiError handleGeneral(Exception ex) {
        log.error("Error no controlado", ex);                  // loguear el detalle
        return ApiError.of("INTERNAL_ERROR", "Error interno del servidor"); // sin detalles al cliente
    }
}

Modelo JPA

El modelo de dominio de BookStore consta de dos entidades: Autor y Libro, con una relación @OneToMany/@ManyToOne bidireccional. Libro guarda la clave foránea autor_id (es el lado dueño), y Autor mapea la colección de libros con mappedBy (es el lado inverso). Ambas entidades usan Lombok para evitar boilerplate y @EntityListeners en Libro para activar la auditoría automática de fechas. Observa cómo @EqualsAndHashCode usa solo el @Id y @ToString excluye la colección libros para evitar el bucle infinito y la carga lazy indeseada.

DTOs y Mapper

La API de BookStore define tres objetos de transferencia: LibroRequestDTO para los datos que el cliente envía al crear o actualizar un libro, LibroResponseDTO para los datos que el servidor devuelve (con el autor embebido como AutorResumenDTO), y LibroMapper para las transformaciones entre DTOs y entidades. El mapper es un componente Spring (@Component) inyectable, con tres métodos: toResponse (entidad → DTO de salida), toEntity (DTO de entrada → entidad nueva) y updateFromDto (DTO de entrada → actualizar entidad existente para el caso PUT). Este patrón de mapper manual es sencillo y explícito; para proyectos con muchas entidades se puede sustituir por MapStruct, que genera las implementaciones en tiempo de compilación.

            libro.getDescripcion(),
            autor,
            libro.getCreadoEn()
        );
    }

37 · Ejemplo — Repository

Repository Layer

El repositorio de libros extiende JpaRepository y añade tres grupos de métodos propios: métodos derivados del nombre para búsquedas simples (existsByIsbn, findByIsbn), una query JPQL con JOIN FETCH para la búsqueda filtrada multipropósito (que evita el problema N+1 cargando el autor junto con los libros en una sola consulta), y un @Modifying @Query para actualizar el stock directamente en la BD sin necesidad de cargar la entidad en memoria. El parámetro de paginación en la query de búsqueda acepta los criterios de forma opcional: cuando un parámetro es null, la condición JPQL :x IS NULL OR … hace que ese filtro se ignore automáticamente.

repository/LibroRepository.javaJava
// Extender JpaRepository nos da gratis: save, findById, findAll,
// delete, count, existsById y sus variantes paginadas
public interface LibroRepository
        extends JpaRepository<Libro, Long> {

    // ① Spring genera la query a partir del nombre del método
    boolean existsByIsbn(String isbn);
    Optional<Libro> findByIsbn(String isbn);
    List<Libro> findByAutorId(Long autorId);

    // ② JOIN FETCH: carga autor y libro en una sola query (evita N+1)
    @Query("""
        SELECT l FROM Libro l
        JOIN FETCH l.autor a
        WHERE (:titulo IS NULL
               OR LOWER(l.titulo) LIKE LOWER(CONCAT('%',:titulo,'%')))
          AND (:genero IS NULL OR l.genero = :genero)
          AND (:autorNombre IS NULL
               OR LOWER(a.nombre) LIKE LOWER(CONCAT('%',:autorNombre,'%')))
        """)
    Page<Libro> buscar(
        @Param("titulo")      String titulo,
        @Param("genero")      Libro.Genero genero,
        @Param("autorNombre") String autorNombre,
        Pageable pageable
    );

    // ③ UPDATE directo: no carga la entidad en memoria (más eficiente para stock)
    @Modifying
    @Query("UPDATE Libro l SET l.stock = :stock WHERE l.id = :id")
    int actualizarStock(@Param("id") Long id, @Param("stock") Integer stock);
}
⚠️
Problema N+1: si haces findAll() y luego accedes a libro.getAutor() en un bucle, JPA lanza una query por cada libro. El JOIN FETCH en la query de búsqueda resuelve esto cargando todo en una sola query.

Service Layer

El service es el corazón de la lógica de negocio. Sigue el patrón interfaz + implementación: LibroService define el contrato público (lo que el controller puede llamar), y LibroServiceImpl contiene la implementación real. Esta separación facilita el testing —el controller puede recibir un mock de LibroService— y deja abierta la puerta a implementaciones alternativas sin cambiar el controller. La clase está anotada con @Transactional a nivel de clase (todas las operaciones de escritura abren transacción), y los métodos de solo lectura sobreescriben con @Transactional(readOnly = true) para optimizar el rendimiento. Las reglas de negocio propias del dominio —como la unicidad del ISBN— viven aquí, no en el controller ni en el repositorio.

@Service
@Transactional                          // ① todas las operaciones abren transacción
@RequiredArgsConstructor                 // ② Lombok: constructor con los campos final
public class LibroServiceImpl implements LibroService {

    private final LibroRepository  libroRepo;
    private final AutorRepository  autorRepo;
    private final LibroMapper      mapper;

    @Override
    @Transactional(readOnly = true)    // ③ readOnly: Hibernate no genera dirty-checking
    public Page<LibroResponseDTO> listar(Pageable p) {
        return libroRepo.findAll(p).map(mapper::toResponse);
    }

    @Override
    @Transactional(readOnly = true)
    public LibroResponseDTO obtenerPorId(Long id) {
        return libroRepo.findById(id)
            .map(mapper::toResponse)
            .orElseThrow(() -> new LibroNotFoundException(id));  // ④ 404 si no existe
    }

    @Override
    public LibroResponseDTO crear(LibroRequestDTO dto) {
        // ⑤ Regla de negocio: ISBN único en todo el catálogo
        if (dto.isbn() != null && libroRepo.existsByIsbn(dto.isbn())) {
            throw new RecursoYaExisteException("Ya existe un libro con ISBN: " + dto.isbn());
        }
        Autor autor = autorRepo.findById(dto.autorId())
            .orElseThrow(() -> new AutorNotFoundException(dto.autorId()));

        Libro libro = mapper.toEntity(dto, autor);
        return mapper.toResponse(libroRepo.save(libro));           // ⑥ save() + convertir a DTO
    }

    @Override
    public LibroResponseDTO actualizar(Long id, LibroRequestDTO dto) {
        Libro libro = libroRepo.findById(id)
            .orElseThrow(() -> new LibroNotFoundException(id));

        // ⑦ Validar ISBN solo si ha cambiado
        if (dto.isbn() != null
            && !dto.isbn().equals(libro.getIsbn())
            && libroRepo.existsByIsbn(dto.isbn())) {
            throw new RecursoYaExisteException("Ya existe un libro con ISBN: " + dto.isbn());
        }
        Autor autor = autorRepo.findById(dto.autorId())
            .orElseThrow(() -> new AutorNotFoundException(dto.autorId()));

        mapper.updateFromDto(dto, libro, autor);                    // ⑧ modifica la entidad en memoria
        return mapper.toResponse(libroRepo.save(libro));           // ⑨ save() detecta que ya existe → UPDATE
    }

    @Override
    public LibroResponseDTO actualizarStock(Long id, Integer stock) {
        if (stock < 0) throw new IllegalArgumentException("Stock no puede ser negativo");
        int filas = libroRepo.actualizarStock(id, stock);           // ⑩ UPDATE directo, sin cargar entidad
        if (filas == 0) throw new LibroNotFoundException(id);
        return obtenerPorId(id);
    }

    @Override
    public void eliminar(Long id) {
        if (!libroRepo.existsById(id)) throw new LibroNotFoundException(id);
        libroRepo.deleteById(id);
    }
}

40 · Ejemplo — Excepciones

Excepciones de dominio

Cada error de negocio se representa con una excepción propia que extiende RuntimeException. Esto tiene dos ventajas: el llamador no está obligado a capturarlas (no son checked), y Spring hace rollback automático en @Transactional cuando se lanza una RuntimeException. Todas estas excepciones son interceptadas por el GlobalExceptionHandler (sección 29), que las convierte al formato ApiError con el código HTTP correcto. El mapeo es deliberado: una LibroNotFoundException siempre produce un 404, una RecursoYaExisteException un 409, etc. Esto centraliza en un único lugar la correspondencia entre el mundo del dominio y el mundo HTTP, manteniendo el service limpio de código de respuesta HTTP.

Buenas Prácticas

1

Arquitectura en capas estricta

Separa Controller → Service → Repository. Los controllers solo gestionan HTTP (no contienen lógica de negocio). Los repositories solo acceden a datos (no contienen lógica de negocio). Los services orquestan la lógica.

2

Usa DTOs, nunca entidades directamente

Nunca expongas entidades JPA en la API. Los DTOs controlan exactamente qué campos entran y salen, evitan referencias circulares de JPA y permiten tener contratos HTTP estables independientes del modelo de datos.

3

Inyección por constructor + campos final

Declara dependencias como private final e inyéctalas por constructor. Usa Lombok @RequiredArgsConstructor. Evita @Autowired en campos: dificulta el testing y oculta las dependencias.

4

Formato de error consistente en toda la API

Define un único record ApiError con codigo, mensaje, detalles y timestamp. Centraliza el mapeo en @RestControllerAdvice. Nunca expongas stack traces al cliente.

5

Externaliza toda la configuración

Usa @ConfigurationProperties con clases tipadas y @Validated. Nunca hardcodees URLs, credenciales o timeouts en el código. Usa variables de entorno para secretos y perfiles para diferencias por entorno.

6

Tests en todos los niveles

Tests unitarios para services (Mockito, sin Spring), tests de capa web para controllers (@WebMvcTest + MockMvc) y tests de repositorio (@DataJpaTest). Solo usa @SpringBootTest para flujos end-to-end críticos.

7

Gestiona el esquema de BD con migraciones

Usa Flyway o Liquibase en todos los entornos. Nunca ddl-auto: update fuera de desarrollo. Las migraciones son versionadas, auditables y reproducibles en cualquier entorno.

8

Pagina siempre las colecciones

Nunca devuelvas listas sin límite desde un endpoint REST. Usa Page<T> con @PageableDefault para controlar el tamaño máximo de respuesta y proteger la BD de consultas masivas.

9

Usa @Transactional(readOnly = true) en lecturas

Marca los métodos de solo lectura con readOnly = true. Hibernate desactiva el dirty-checking, mejora el rendimiento y documenta la intención del método.

10

Versiona tu API desde el primer día

Prefija todas las rutas con /api/v1/. Cuando necesites cambios incompatibles, crea /api/v2/ sin eliminar la versión anterior. Los clientes existentes no deben romperse por cambios internos.
